## Баги по severity

### 🔴 №1 Critical — раздел «Аналитика» полностью сломан

- **Шаги:** войти админом/менеджером → `/analytics`.
- **Ожидалось:** метрики и графики. **Фактически:** ErrorState «Поле недоступно. Возможно, схема обновлена…», 4 × HTTP 400 от PostgREST.
- **Причина:** [src/features/analytics/hooks/useAnalyticsData.js:68,71](src/features/analytics/hooks/useAnalyticsData.js#L68) — `.is('deleted_at', null)` на `k24_orders`, но колонки `deleted_at` в этой таблице **нет** (есть только в `k24_production_logs`). Внесено в R17.0 без сопутствующей миграции.
- **Фикс:** убрать фильтр (или добавить колонку миграцией). Одна строка × 2.
- Скриншот: `docs/screenshots/qa-2026-07-04/bug-analytics-400.png`.

### 🔴 №2 Critical — Realtime не работает во всём приложении

- **Шаги:** два таба, в одном добавить комментарий к заказу → во втором не появляется. WS-фреймы: сервер отвечает `Unable to subscribe to changes… Please check Realtime is enabled` на каждую подписку.
- **Причина:** publication **`supabase_realtime` в БД пуста** — ни одной таблицы (`SELECT * FROM pg_publication_tables WHERE pubname='supabase_realtime'` → 0 строк). Вероятно, потеряно при переезде на dedicated-проект 2026-05-11.
- **Затронуто:** живые обновления канбана и списков заказов, комментарии (R17.1), подзадачи, все 5 каналов планировщика (R12), звуковые уведомления о новых этапах, ActiveShiftsWidget (R15.4), склад. Всё обновляется только по перезагрузке; деградация тихая, поэтому её не замечали.
- **Фикс:** `ALTER PUBLICATION supabase_realtime ADD TABLE k24_orders, k24_production_logs, k24_order_comments, k24_order_status_history, k24_order_subtasks, k24_order_items, k24_plan_overrides, k24_settings, k24_shift_entries, k24_materials, k24_material_transactions, k24_pack_designs;` (список сверить с каналами в коде).

### 🟠 №3 Major — заказ невозможно штатно вывести из статуса «Новый»

- **Шаги:** заказ в статусе «Новый» → на странице заказа нет кнопки «→ Дизайн» ни у одной роли, включая admin; перетаскивание в канбане отклоняется с тостом «У роли „admin" нет права продвигать этап „Новый"».
- **Причина:** [src/shared/constants.js:276](src/shared/constants.js#L276) `canAdvanceFrom()` при загруженных динамических правах проверяет `stage:new` в `k24_role_permissions` — такого права **нет ни у одной роли** (и нет в UI редактора прав). Legacy-fallback `admin: true` недостижим, пока динамические права загружены. Тот же чек в `updateOrderStatus` ([useOrders.js:333](src/features/orders/hooks/useOrders.js#L333)) блокирует канбан.
- **Подтверждение из истории:** все реальные переходы из «Новый» — force-прыжки через AdminOrderEditor (new→pouring, new→prepress, new→print, мимо маршрута). Команда неосознанно живёт на обходном пути, ломая маршрутную дисциплину и статистику этапов.
- **Фикс:** сид-миграция `stage:new = true` для admin/manager (по образцу 056) или спец-кейс `'new'` в `canAdvanceFrom`.

### 🟠 №4 Major — не-3D заказ с БОПП-пакетом нельзя продвинуть в «Упаковку»

- **Шаги:** sticker_cut с `bopp_bag=true` на этапе «Резка» → кнопка «→ Упаковка» предлагается → клик → тост «Этап „Упаковка" не входит в маршрут заказа».
- **Причина:** [src/features/orders/hooks/useOrders.js:308](src/features/orders/hooks/useOrders.js#L308) — `updateOrderStatus` перечитывает заказ как `select('order_type, design_status, need_lam, number')` **без `bopp_bag`** → в `getOrderRoute` ([constants.js:176](src/shared/constants.js#L176)) `order.bopp_bag === true` ложно → packaging выкинут из маршрута → `isStageAllowed` отклоняет. Кнопка при этом строится по полному объекту заказа — отсюда рассинхрон «предложили, но не пустили».
- **Фикс:** добавить `bopp_bag` в select (одно слово).

### 🟠 №5 Major — completion-check мёртв для обычных заказов (PGRST203)

- **Шаги:** внести данные этапа на любом одиночном (не dual-track) заказе → в консоли `PGRST203: Could not choose the best candidate function` (поймано 5+ раз за прогон); авто-предложение «этап завершён → перейти дальше» никогда не появляется.
- **Причина:** в БД **две перегрузки** `check_stage_completion(uuid,text)` и `(uuid,text,text DEFAULT NULL)` (первая — миграция 003, вторая — 008+). Вызов с двумя именованными аргументами в [useOrders.js:493](src/features/orders/hooks/useOrders.js#L493) неоднозначен → PostgREST 300 → `captureError` → `isComplete=false` навсегда. Остальные вызовы (с `p_track`) резолвятся нормально.
- **Побочка:** Sentry засоряется этой ошибкой на каждом вводе данных.
- **Фикс:** миграция `DROP FUNCTION check_stage_completion(uuid,text)` (3-арг версия с DEFAULT её полностью покрывает) — либо всегда передавать `p_track: null` во фронте.

### 🟡 №6 Minor — xlsx-выгрузка без имени файла

Выгрузка из /reports скачивается как `download` без расширения/имени. Содержимое корректно (проверено SheetJS: суммы совпали с UI и БД).

### 🟡 №7 Cosmetic — вкладка «Архив» склада: неверная единица измерения

Для позиции с `unit='m'` в колонке «Остаток» показано `m2` (у архивной таблицы, похоже, захардкожена единица).

## Наблюдения (не баги, но стоит взглянуть)

1. **Забытая смена 26+ часов** — у постпечатника активная смена с 05:46 предыдущего дня (виджет «Активные смены» честно тикает 26ч 45мин). Нет авто-стопа или предупреждения; влияет на отчёт «Отработанные часы».
2. **PDF тех-карты весит 5.9 МБ** (PNG 116 КБ при том же контенте). Для телефонов в цеху — тяжело. Причина: canvas scale 2 кладётся в PDF без JPEG-сжатия.
3. **PackDesignsForm — частичная запись при сбое сети:** batch «Сохранить» шлёт N отдельных INSERT; при обрыве часть видов теряется. Частичный фидбэк работает (тост «Сохранено 3, ошибки на #4» — R13.2 ✓), но авторетрая нет. Поймано живьём (2 из 4 видов не записались с первого раза).
4. **Шкала «Препресс (видов)»** для 3D-пака: target = кол-во видов (1), а поле формы называется «Подготовлено к печати (шт)» — ввёл 12 шт и получил 999%. Семантика «виды vs штуки» путает.
