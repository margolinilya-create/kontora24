# Промт: Полное тестирование Kontora24 (технический + функциональный + визуальный)

Скопируй всё, что ниже, в Claude Code, открытый в корне репозитория `kontora24`.

---

Ты — QA-инженер. Проведи полное тестирование Kontora24 — MES/WMS для стикерного производства. Это Vite 8 + React 19 SPA с Supabase (PostgreSQL + RLS + Realtime + Storage), деплой на Vercel. Прочитай `CLAUDE.md` перед началом — там описаны роли, маршруты заказов, схема БД и вся история релизов (R8–R17).

Ничего не чини без моего подтверждения — сначала полный отчёт. Работай поэтапно, после каждого этапа давай краткую сводку.

## ⚠️ Критическое ограничение: боевая база данных

Dev-сервер подключается к **продакшн-проекту Supabase** (`pulzirakjqehsulmjhdj`) с реальными заказами, клиентами, остатками склада и сменами живого производства (6 сотрудников, старт 2026-05-11). Правила:

1. **Всё, что создаёшь, помечай маркером `E2E-ТЕСТ`**: название сделки `E2E-ТЕСТ <что проверяем>`, клиент `E2E-ТЕСТ Клиент`, позиции склада `E2E-ТЕСТ <материал>`.
2. **После каждого модуля удаляй свои тестовые данные** (заказы — через отмену/удаление в UI; в конце прогона — финальная зачистка всех сущностей с маркером). В отчёте перечисли, что создавалось и что удалено.
3. **Никогда не редактируй и не удаляй реальные данные**: чужие заказы, клиентов, номенклатуру склада, пользователей, k24_settings.
4. **Не гоняй инвентаризацию по реальным позициям склада** — она создаёт корректирующие транзакции. Проверяй инвентаризацию только на своей `E2E-ТЕСТ` позиции.
5. **Не меняй права в `/settings → Права ролей`** (k24_role_permissions — общие для всех). Если проверка требует изменить чекбокс — зафиксируй исходное состояние и верни его сразу после проверки.
6. **Не удаляй и не создавай пользователей** через Настройки → Пользователи (только визуальная проверка формы без submit).
7. Приходы/расходы склада — только по своей тестовой позиции.

## Этап 0. Подготовка окружения

1. Проверь `.env.local` — нужны `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` (образец в `.env.example`). Если нет — остановись и запроси у меня.
2. `npm ci`, затем `npm run dev` — приложение на `http://localhost:5173`.
3. Playwright уже настроен (`playwright.config.js`: проекты desktop + mobile/iPhone 14, webServer поднимается сам). Chromium в этом окружении предустановлен — `npx playwright install` не нужен.
4. Изучи `e2e/helpers.js` — там готовые хелперы: `login()` (админ `mib@pnhd.ru` / `Kontora24!`), `emulateRole()` (RoleSwitcher — эмуляция ролей из-под админа, отдельные креды не нужны), `dismissShiftModal()`, `clickViewTab()`, `ensureSidebarOpen()`. Используй их, а не пиши свои.
5. Во всех тестах собирай `console.error`, `console.warn`, `pageerror`, упавшие network-запросы (кроме заблокированного Sentry, если он в списке).

## Этап 1. Статический и технический аудит

1. **Пайплайн:** прогони `npm run check` (ESLint + ~645 Vitest-тестов + production build) и `npm run test:security`. Все падения — в отчёт с полным выводом.
2. **Консоль при загрузке:** залогинься, пройди по всем разделам (Dashboard, Заказы, все очереди производства, Планирование, Склад, Клиенты, Аналитика, Отчёты, Кабинет, Настройки, Помощь). Зафиксируй ВСЕ ошибки и warning'и: React key warnings, controlled/uncontrolled inputs, Supabase-ошибки (RLS deny, missing column), 4xx/5xx запросы, дубликаты realtime-каналов.
3. **Структура кода:** найди `console.log`-мусор, неиспользуемые экспорты, дублирующиеся константы (известный анти-паттерн: локальные копии вместо импорта из `shared/constants.js` — см. R15.5), захардкоженные значения, которым место в `k24_settings`.
4. **Производительность:** размер prod-бандла (`npm run build`, обрати внимание на чанки >500 КБ — jsPDF/html2canvas/recharts/xlsx), время до интерактивности на dev и на preview-сборке, время рендера `/orders` при текущем объёме данных. Тестовые данные для нагрузки НЕ генерируй в боевой БД — оцени на реальном объёме и через React Profiler.
5. **PWA/offline:** service worker регистрируется, `offline.html` отдаётся без сети, OfflineIndicator появляется при `context.setOffline(true)`.

## Этап 2. Функциональное тестирование (E2E через Playwright)

Для каждого модуля: happy path + граничные случаи + невалидный ввод. На каждый баг — шаги воспроизведения. Новые spec-файлы клади в `e2e/` рядом с существующими (`auth.spec.js`, `orders.spec.js`, `role-access.spec.js`, `planner.spec.js` — сначала прогони их как регресс-базу).

### 2.1 Авторизация и RBAC (L2)

- Вход админом, выход, невалидный пароль (ошибка по-русски, без белого экрана).
- Через `emulateRole()` пройди все 4 роли: manager, designer, printer, post_printer. Для каждой сверь видимость пунктов Sidebar с матрицей из CLAUDE.md.
- **Финансы скрыты от работников:** под designer/printer/post_printer нигде не видны `price_final`, себестоимость, маржа — проверь карточку заказа, OrderDetailPage, FinanceTab, AdminOrderEditor (R14.8), ReportsPage (без `view:finance` видна только вкладка «3D отдел»).
- **Прямой заход по URL, а не только скрытие кнопок:** под каждой ролью открой напрямую `/settings`, `/reports`, `/warehouse`, `/analytics`, `/production/plan` — AuthGuard должен блокировать согласно правам.
- ShiftReminderModal показывается воркерам при входе, «Завершить смену» синхронизирует кнопку в Кабинете без перезагрузки (R15.0).

### 2.2 Заказы: создание и жизненный цикл

- **Создание (`/orders/new`):** 3 секции (Сделка / Заказ / Отгрузка). Zod-валидация обязательных полей: `order_type`, `qty`, `width_mm`, `height_mm`, `price_final`, `client_name`, `deadline` — без них submit заблокирован, ошибки по-русски.
- Пресеты размеров A7/A6/A5 заполняют width/height. Условные поля: `stickers_per_pack` только для стикерпаков, `film_type_stickers` только для stickerpack3D, поля доставки только при `delivery_type=delivery`, `source_referrer` только при source=referrer.
- Граничные случаи: qty 0 / 1 / 100000, размер 0 и отрицательный, дробные мм, запятая вместо точки, дедлайн в прошлом.
- Drop-zone превью: JPG/PNG/WEBP ≤ 2 МБ принимается, 3 МБ и PDF — отклоняются с понятной ошибкой. Ctrl+V из буфера (R17.1). Превью после создания попадает в тех-карту (`kind='preview'`, sample_print-фото в тех-карту утекать не должно — R14.6).
- ClientCombobox: поиск существующего + создание на лету. Второй заказ на того же клиента не плодит дубль в `k24_clients`.
- FilmSelect/LaminationSelect (R16.1): опции строятся из остатков склада, выбор отдаёт и `materialId`, и `code`.
- MaterialForecast (R8.1): live-расчёт метров плёнки/смолы/БОПП при вводе размеров, green/red индикация против остатков. Сверь 2–3 расчёта вручную по формулам из `src/features/orders/lib/material-forecast.js` (плёнка 1230/970/1220, смола 0.1444 г/см², стикеры 3D-пака — `computeStickerFilmMeters`, БОПП-матчинг `pickBoppMaterial` с допуском +4 мм).
- Multi-variant (R8.3): «Кол-во видов изделий» 2–6 → таблица размеров/тиражей, submit блокируется при незаполненных видах (R14.7). После создания — variant-подзадачи на странице заказа.
- **Список `/orders`:** 3 вида (карточки по отделам / канбан / календарь), переключение сохраняется. Поиск по номеру, `custom_number` и имени клиента (R13.0). Фильтры по датам и отделам, SavedFilters сохраняются в БД и переживают relogin.
- **DnD-канбан:** перетаскивание в следующую разрешённую колонку работает; в колонку вне маршрута (`isStageAllowed`) — заблокировано. Skip-stages: заказ с `design_status='provided'` минует design; с `need_lam=false` — lamination; без БОПП и не-3D — packaging.
- **Карточка заказа:** StatusSwitcher двигает только на следующий этап маршрута; StatusOverride (admin/manager) откатывает назад; при грязном статусе вне маршрута OrderStepper показывает предупреждение + кнопку возврата. AdminOrderEditor: инлайн-правки всех 7 секций сохраняются. Комментарии: добавить/редактировать/удалить с ConfirmDialog, метка «· изменено», realtime-обновление во втором табе (R17.1).

### 2.3 Производственный цикл (3 маршрута)

Создай три тестовых заказа и провези каждый через маршрут целиком (двигай статусы под эмуляцией соответствующих ролей — designer/printer/post_printer):

1. **Обычный стикер:** `new → design → prepress → print → lamination → cutting → packaging → otk → done`. На каждом этапе — ввод данных через ProductionLogForm; проверь валидацию R15.1: обязательные поля и отрицательные числа = error (блок submit), превышение поступившего с прошлого этапа = warning (toast, но submit проходит).
2. **sticker3D:** через `pouring`; заливка: вводятся «Залито» + «Брак», `stickers_good` считается автоматически; логи попадают в историю, брак не уходит в минус кроме drying-линии (R14.4: total < 0 → красный бар «нужна допечатка»).
3. **stickerpack3D (dual-track):** после prepress OrderStepper раздваивается на треки ФОН/СТИКЕР (R16.0); CurrentStageWidget показывает две карточки учёта side-by-side, каждая пишет лог со своим `track`; PackDesignsForm — поэвидовый ввод на prepress (план)/print/cutting/pouring; заказ продвигается на общий этап только когда оба трека завершены; кнопка «Завершить „X“ → Y» с ConfirmDialog в SubtaskTrackBlock.

- Очереди `/production/*`: заказ виден в очереди своего этапа, пропадает после продвижения; sticker-трек stickerpack3D в pouring виден на `/production/pouring` (R14.3).
- Редактирование и soft-delete лога (`deleted_at`) корректно пересчитывают прогресс-бары этапа.
- Списание материалов: после лога печати по тестовому заказу с тестовой плёнкой появляется `material_transaction` с привязкой к заказу; при `film_material_id` списывается именно выбранная позиция (R16.1). Проверяй ТОЛЬКО на своей E2E-ТЕСТ позиции склада.

### 2.4 Тех-карта, стикеры, экспорт

- Тех-карта A4: все поля заказа на месте, превью подгружается, экспорт PNG и PDF не обрезают контент (известные грабли: `scrollWidth/scrollHeight`, `imageTimeout` — см. CLAUDE.md). Открой полученный PNG и проверь визуально: шрифты (Guidy для даты, Modulord для номера) отрисованы, не tofu; кириллица в названии сделки не ломается. Проверь на заказе с длинным названием (100+ символов) и длинным комментарием (500+): ничего не вылезает и не перекрывается.
- Кнопка «Печать»: `@media print` скрывает интерфейс, карта не разваливается (проверь через `page.emulateMedia({ media: 'print' })` + скриншот).
- ProductionSticker / DeliverySticker 120×75 мм: генерация, QR-код валиден (декодируй), экспорт.
- Имена файлов экспорта — через `orderFileSlug` (формат `ORD-NNNN`), в UI при этом номер без префикса.

### 2.5 Склад

- Приход с суммой → `unit_cost` пересчитывается по WAC (сверь вручную: два прихода разной цены → средневзвешенная). Расход. История транзакций.
- StockModal preflight: под ролью без `material:add_transaction` кнопка недоступна (R17.0).
- Мультифильтр категорий, поиск, unit dropdown.
- Архивирование (admin/manager, R13.1): позиция уходит во вкладку «Архив», исчезает из основных списков и селектов формы заказа, история сохраняется; разархивирование возвращает. Hard delete: у позиции с транзакциями заблокирован (toast «можно только архивировать»), у чистой — работает.
- Инвентаризация — только на своей E2E-ТЕСТ позиции: ввод факта → транзакция `reason='Инвентаризация'`, `delta = факт − текущий`.
- Виджет «План трат» (R13.1) и план-факт tooltip (R14.1): tooltip не обрезается, номера заказов кликабельны/корректны.

### 2.6 Отчёты, аналитика, кабинет

- **Сдельная оплата** — пересчитай вручную по своим тестовым логам: заливка 1.0 ₽/шт (`stickers_good`), выборка фонов 0.5 ₽/шт, сборка 3D `packs_assembled × stickers_per_pack × 0.5`, упаковка 1.5 ₽/шт, выборка sticker3D (stage `selection`) без множителя (R14.6). Этапы печать/ламинация/резка/дизайн/препресс в сдельную НЕ входят.
- Unit Economics: колонки «Излиш. шт» / «Излиш. %» (R15.3), «Разница ₽/%» = `price_final − себестоимость материалов` (R17.5).
- **XLSX-выгрузка:** скачай файл, открой программно (SheetJS в node) и сверь 2–3 суммы с данными на экране и в БД.
- Периоды: «Сегодня» и «Свой» (два date-инпута) фильтруют и низ, и верх диапазона (R13.3/R15.2). Ошибка запроса → ReportError с кнопками «Обновить» / «Скопировать код».
- Аналитика: виджеты производства (штучные + погонные метры печать/ламинация/резка — R17.5), tile с нулём и `alwaysShow=false` скрывается. Пересчитай 2–3 метрики вручную.
- Dashboard: ActiveShiftsWidget с live-таймером, клик по метрикам «Заказов в работе» / «К сдаче сегодня» открывает Modal со списком, disabled при нуле (R15.4).
- Кабинет: старт/стоп смены, фактическая длительность в toast, виджеты кликабельны → Modal, график с toggleable-кривыми.

### 2.7 Планировщик (бета, `/production/plan`)

- Доступ только admin + manager.
- Список заказов слева, календарь с 7 бакетами (design / prepress / oprl_print / oprl_cut / post_3do / post_osk / passive — R17.3). Селект «Горизонт: 1/2/3 месяца».
- DnD чипа на другой день: режим «Каскад» закрепляет только сдвинутый этап, «Только этап» — все; перенос в чужой бакет блокируется info-toast. Закрепление переживает reload (`k24_plan_overrides`), «открепить» возвращает автораскладку.
- Изменение норм/ёмкости в `/settings → Производство (бета)` пересчитывает план (⚠️ зафиксируй исходные значения и верни после проверки).
- Unit-база уже есть — 78 тестов в `src/features/production-planner/lib/*.test.js` + `e2e/planner.spec.js`; прогони их до ручных проверок.

### 2.8 Realtime и персистентность

- Два таба (две `page` в одном контексте): смена статуса заказа в одном табе появляется во втором без reload (канбан, карточка заказа, комментарии, планировщик).
- Reload после каждого модуля — данные на месте, фильтры/вид списка сохранены.
- Обрыв сети (`context.setOffline(true)`): OfflineIndicator, действия не теряются молча — понятная ошибка; после восстановления приложение живо без reload.
- Истечение сессии: сброс токена → редирект на /login без белого экрана.

## Этап 3. Визуальное тестирование

1. Скриншоты каждого экрана (все разделы, все вкладки, ключевые модалки, тех-карта, канбан, планировщик) в разрешениях: 390×844 (телефон — **основной сценарий, цех работает с телефонов**), 768×1024, 1366×768, 1920×1080. Каждое — в светлой И тёмной теме. Сохрани в `./docs/screenshots/qa-<дата>/` с понятными именами. За основу возьми существующий `e2e/screenshots.spec.js`.
2. Проанализируй каждый скриншот: обрезанный текст, наложение элементов, горизонтальный скролл, кнопки за пределами экрана, нечитаемые контрасты (особенно в тёмной теме), «поехавшие» таблицы при длинных названиях.
3. Mobile-специфика: все тач-таргеты ≥ 40px, DnD-канбан юзабелен пальцем, bottom-sheet календаря, burger-меню, формы этапов вводимы одной рукой.
4. Стресс данных (на своих тестовых сущностях): название сделки 100+ символов, price_final 9 999 999.99, длинный email клиента — верстка не ломается.
5. Состояния UI: пустые списки (нулевые состояния), скелетоны при загрузке, disabled-кнопки, фокус на инпутах, ErrorState с кнопкой «Повторить».

## Этап 4. Отчёт

Собери всё в `TEST_REPORT.md` в корне репозитория:

- **Сводка:** сколько проверок, сколько прошло/упало; статус `npm run check` и существующих e2e.
- **Баги по severity:** Critical (падение, потеря/порча данных, утечка финансов работнику, сломанный экспорт) / Major (функция не работает) / Minor (верстка, UX) / Cosmetic. Для каждого: шаги воспроизведения, ожидаемое vs фактическое, скриншот, предполагаемая причина в коде (файл:строки, функция).
- **Сверка с известными ограничениями:** прежде чем записать баг, проверь разделы «Не сделано осознанно» в CLAUDE.md (R14–R17) — известные design decisions багами не считаются, вынеси их в отдельный список «Подтверждённые известные ограничения».
- **Чистота данных:** список созданных E2E-ТЕСТ сущностей и подтверждение удаления каждой.
- **Регресс-чеклист** — таблица для повторных прогонов после будущих правок (новые spec-файлы в `e2e/` — это и есть автоматизированная её часть).
- **Рекомендации** по производительности и рефакторингу (не более 10, по приоритету).

После отчёта остановись и жди моего решения, какие баги чинить.
