# R25 — эталон отчётов

Критерий ТЗ R25 («Общие требования»): отчёты «Сдельная оплата», «Качество» и
«3D отдел» за май–ноябрь 2026 не должны меняться ни после одной фазы.

| Файл | Что |
|------|-----|
| `r25_reports_baseline.sql` | Только SELECT. Агрегаты оплаты по сотруднику/этапу/типу/форме, итог по сотруднику, брак и «Качество» по этапам, колонки «3D отдела» по виду, операции склада и остаток на cutoff |
| `r25-baseline.json` | Эталон, снят с прода 2026-11-17 (окно 2026-05-01 … 2026-11-17 00:00 UTC) |
| `compare.mjs` | Сравнение эталона с новым прогоном (строки сопоставляются по ключу, допуск 0.005) |

Персональных данных нет — только `worker_id`, номера заказов и id материалов.

## Как перепроверить после фазы

1. Выполнить `r25_reports_baseline.sql` в проде (Supabase MCP `execute_sql`,
   project `pulzirakjqehsulmjhdj`, или SQL Editor). Сохранить ответ в файл —
   подходит и «чистый» объект, и ответ вида `[{"baseline": {...}}]`.
2. `node scripts/baseline/compare.mjs /path/to/new.json`
   (или `node scripts/baseline/compare.mjs <эталон.json> <новый.json>`).
3. Exit 0 — совпадает. Exit 1 — список расхождений `путь: было → стало`.

## Что может легитимно разойтись

- Сотрудник удалил/исправил старый лог задним числом (`deleted_at`, правка значений).
- Статус заказа в `three_d[].status` (заказ дошёл до «Готов»).
- `bonus_rates` поменяли в настройках (блок `rates` и суммы `amount`).

Если окно нужно расширить до конца ноября (после 30.11) — поднять cutoff в
`params` до `2026-12-01` и пересохранить эталон осознанно, отдельным коммитом.

## Контроль квирков

`quirk_fields_off_stage` — поля оплаты на «чужих» этапах. До R25.0 отчёты
платили по полю без проверки этапа; на эталоне все четыре суммы = 0, поэтому
переход на единый `computeLogPayout` (оплата только на своём этапе) не меняет
цифры за май–ноябрь.
